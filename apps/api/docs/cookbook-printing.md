# Printed cookbooks: operator setup and launch gate

Fridgie's print flow is additive commerce. It never gates recipes or the app
behind a subscription. Drafting and deterministic PDF preview work without
payment or printer credentials; quote, payment authorization, and fulfillment
fail closed until their real sandbox configuration is present.

## What ships in this repository

- Private, owner-authorized Firestore drafts with optimistic revisions.
- Immutable snapshots with copied recipe text, rights decisions, render-engine
  version, PDF hashes, and append-only order events.
- Classic, Modern, and Photo-forward layouts generated by the same layout plan.
- 7 x 10 full-color Lulu interiors at 7.25 x 10.25 inches including bleed,
  embedded OFL Space Mono, 0.5-inch-safe content, provider SKU page limits,
  multiple-of-four padding, page numbers, sections, contents, and index.
- A one-page integrated cover PDF, page-count-derived softcover spine, and
  casewrap gating until exact Lulu template geometry is supplied.
- Local preflight for rights, missing/low-resolution photos, overflow, empty
  pages, page count, spine constraints, and casewrap provider validation.
- Private GCS objects with short-lived app links, seven-day Lulu links, hashes,
  retention metadata, and a cleanup/reconciliation job.
- Provider-neutral service boundaries, a Lulu sandbox adapter, Stripe
  PaymentSheet/manual capture, signed webhooks, retries, refunds/releases,
  tracking, order history, and operator-approved reprints from the immutable
  purchased PDFs.

## Important Lulu production blocker

As checked against Lulu's public OpenAPI on 2026-09-29, Lulu normalizes files
only after `POST /print-jobs/`. The public API documents neither a standalone
file-validation operation nor a cancellation mutation. `external_id` is a
reference, not an idempotency key. The 2026 product sheet's dotted SKU format
also conflicts with the OpenAPI's older 27-character limit, and first-party
examples disagree on `shipping_option` versus `shipping_level`.

For that reason, live printing remains blocked unless
`PRINT_LULU_VALIDATION_ACKNOWLEDGED=true` and
`PRINT_PRODUCTION_ENABLED=true`. Set the acknowledgement only after Lulu has
confirmed, in writing or via an approved private contract, a safe normalization,
autopay, and cancellation/recovery sequence for this account. The code uses a
24-hour production delay and authorizes the customer's card first; it captures
only after Lulu reports an accepted production state. This reduces risk but is
not a substitute for that provider confirmation.

## 1. Private storage and Firebase

Create a dedicated private GCS bucket, then set `PRINT_STORAGE_BUCKET`.
Do not add Firebase download tokens or public ACLs. Grant the Cloud Run runtime
service account only object create/read/delete for this bucket and the ability
to sign V4 URLs (`iam.serviceAccounts.signBlob`, commonly via Service Account
Token Creator on itself). Add a bucket lifecycle as a backstop for
`private-print/previews/`, but keep the scheduled cleanup job below because
order and preview retention differ.

The named Firestore database is `fridgie-db`. Enable TTL on:

- `cookbookPrintQuotes.expireAt`
- `cookbookPrintWebhookEvents.expireAt`

All print collections are server-only and every mutable/private document stores
`ownerUid`; mobile never talks to Firestore or Storage directly for printing.
No existing recipe migration is required.

Preview files expire after two days. Purchased PDFs default to 120 days so a
reviewed replacement can reuse the exact bytes rather than re-render mutable
images; set `PRINT_ORDER_ARTIFACT_RETENTION_DAYS` to the retention period in the
published privacy policy. Shipping addresses and order events are private
commerce records and must be covered by the account-deletion/legal-retention
runbook. Never place addresses in logs, analytics, or provider error messages.

## 2. Lulu sandbox

Create a separate Lulu sandbox account and API application. Set:

```text
LULU_ENV=sandbox
LULU_CLIENT_KEY=...
LULU_CLIENT_SECRET=...
```

The two launch SKUs are the current 2026 7 x 10 Executive, full-color standard,
80# coated white, matte products:

- softcover: `0700X1000.FC.STD.PB.080CW444.MXX`
- casewrap hardcover: `0700X1000.FC.STD.CW.080CW444.MXX`

Before enabling any production flag, run authenticated sandbox contract probes
that prove all of the following for the chosen account and exact SKUs:

1. `/shipping-options/` accepts `country` and `state`.
2. `/print-job-cost-calculations/` accepts the configured
   `LULU_COST_SHIPPING_FIELD` (schema default: `shipping_option`).
3. Both dotted SKUs are accepted.
4. `/print-jobs/` accepts top-level line-item `pod_package_id`, `interior`, and
   `cover` with MD5 sums.
5. A deliberately invalid file is rejected predictably and a valid job reaches
   an accepted state without unexpected production.
6. A timed-out create can be found via list `search`, then exact client-side
   `external_id` matching, before any retry.
7. The observed `Lulu-HMAC-SHA256` encoding is recorded. The bootstrap verifier
   accepts canonical 64-hex or Base64 only and always compares raw-body HMAC in
   constant time.
8. Signed URLs stay usable through normalization and retry timing.

Checkout collects a delivery phone matching Lulu's documented 8-20 character
carrier pattern. Address subdivision values sent as `state_code` must be 2- or
3-letter ISO-3166-2 suffixes (for example `ON`, not `Ontario`); they are
mandatory for AU, CA, MX, and US destinations. Both mobile and the server reject
invalid values before requesting a provider quote.

Never hardcode sandbox card details from help articles; Lulu's current official
articles conflict. Use the current authenticated sandbox portal.

Configure Lulu's webhook as:

```text
https://api.fridgie.ca/api/print/webhooks/lulu
```

Subscribe to `PRINT_JOB_STATUS_CHANGED`. The handler verifies the raw-body HMAC
and then fetches the canonical job from Lulu before changing local state.

## 3. Stripe, wallets, and retail tax

Use matching test credentials with Lulu sandbox:

```text
STRIPE_SECRET_KEY=sk_test_...
STRIPE_PUBLISHABLE_KEY=pk_test_...
STRIPE_WEBHOOK_SECRET=whsec_...
```

Configure the webhook endpoint:

```text
https://api.fridgie.ca/api/print/webhooks/stripe
```

At minimum subscribe to:

- `payment_intent.amount_capturable_updated`
- `payment_intent.succeeded`
- `payment_intent.payment_failed`
- `payment_intent.canceled`
- `charge.refunded`
- `refund.failed`

The order is durably created before its PaymentIntent. One manual-capture
PaymentIntent and a stable Stripe idempotency key are used per order. A verified
authorization webhook atomically queues provider submission and returns without
calling Lulu; the scheduled reconciliation worker claims that durable work. The
client result never fulfills an order. Transient Lulu failure keeps a recoverable order and card
authorization. Terminal rejection releases the authorization or issues an
idempotent refund after capture.

Cancellation is automatic only while the durable order is still
`awaiting-payment`. The server first writes a transactional cancellation fence,
which prevents any concurrent provider claim, and only then releases payment.
Once submission starts—or its outcome is ambiguous—cancellation is a reviewed
support case because Lulu exposes no safe cancel mutation.

When Stripe Tax is enabled, the quote stores its Calculation id and attaches it
to the manual-capture PaymentIntent through `hooks.inputs.tax.calculation`.
Stripe creates the Tax Transaction only after capture succeeds, automatically
creates a full tax reversal for this product's full-order refunds, and
counter-reverses it if the refund later fails. Fridgie never also calls the
manual Tax Transaction APIs. A refund remains `refund-pending` until
`charge.refunded`; `refund.failed` returns the order payment to `paid` and
requires support follow-up. Reconciliation records the association's committed
Tax Transaction id or private error status for operator audit. Stripe does not
automatically reverse tax for disputes, so disputes require a separate reviewed
policy before launch.

Enable Stripe Tax only after registrations, origin, printed-book tax code, and
shipping tax treatment are configured. Lulu's tax is Fridgie's vendor-side COGS
tax, not necessarily the customer's retail tax. Production pricing refuses to
silently omit retail tax unless an operator explicitly sets
`PRINT_ALLOW_UNAVAILABLE_TAX=true` after legal review.

On mobile, expose the same publishable key as
`EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY`. Apple Pay uses merchant identifier
`merchant.com.nairdrie.fridgie`; create that identifier/certificate in Apple and
Stripe, enable the entitlement, and rebuild the native app. Enable Google Pay
in Stripe. Wallets require a dev/EAS/native build and physical-device testing;
they do not work in Expo Go.

## 4. Reconciliation, cleanup, and alerts

Run this job every 10-15 minutes from Cloud Run Jobs/Scheduler with the same
runtime identity and secrets:

```bash
cd apps/api
bun jobs/printReconciliation.ts
```

It polls nonterminal Lulu jobs (webhooks can be delayed or deactivated), applies
idempotent transitions/tracking, resumes expired original/reprint leases, and
deletes artifacts whose private metadata retention has elapsed. Eligible orders
use a persisted fair-rotation cursor, so long-lived production/shipping rows do
not starve newly authorized work. It also completes an interrupted idempotent
Stripe release/refund after a known terminal provider rejection. Every ambiguous
create first exact-matches its stable external id and waits at least
`PRINT_AMBIGUOUS_RETRY_MINUTES` (15 by default) before another POST. Alert on a
nonzero exit status, `submission-unknown`, provider rejection, Stripe capture
failure, failed/pending Stripe Tax associations, and webhook deactivation.

Reprint requests do not automatically spend money at Lulu. Support must verify
the original shipment and approve the replacement. With the original private
PDFs still inside retention, enable the execution gate for the operator job and
run it with the exact order id:

```bash
cd apps/api
PRINT_REPRINT_EXECUTION_ENABLED=true bun jobs/submitApprovedReprint.ts order_...
```

The job exact-matches its own reprint external id before submitting, reuses the
original immutable PDFs and address, preserves the earlier provider id in order
history, and then returns to ordinary webhook/reconciliation tracking. Keep the
gate false in the normal API service unless an operator-controlled environment
requires it.

## 5. CI deployment and one-time worker bootstrap

Printing is opt-in at deployment time. With the GitHub repository variable
`PRINT_COMMERCE_ENABLED` unset or `false`, the existing production API deploy
keeps its original environment/secrets and does not touch a print job. CI also
checks the current Cloud Run service before applying its full replacement flag
set: if it finds a manually attached `LULU_*`, `PRINT_*`, or `STRIPE_*` binding
while the gate is off, it fails instead of silently deleting that binding.

When the gate is exactly `true`, CI validates every non-secret setting, checks
that all five Secret Manager entries have an enabled `latest` version, checks
the private bucket, job, job-level invoker policy, and scheduler, then binds the
complete print configuration to the API candidate. Before promotion it updates
`fridgie-print-reconciliation` to the same verified image and replaces the
job's application-level command, identity, resources, retry policy,
environment, and secrets. Optional platform attachments that are not part of
the bootstrap below (for example VPC or volume settings) remain inherited and
must be reviewed separately if an operator later adds them.
This is deliberately stricter than the Discover worker's image-only update:
reconciliation is part of the payment and fulfillment safety boundary.

### Required Secret Manager entries

Create these exact secret names. Add test values for the staff sandbox or live
values for production; never mix Lulu sandbox with Stripe live mode.

- `fridgie-lulu-client-key`
- `fridgie-lulu-client-secret`
- `fridgie-stripe-secret-key`
- `fridgie-stripe-publishable-key`
- `fridgie-stripe-webhook-secret`

Grant `roles/secretmanager.secretAccessor` on each secret to
`fridgie-api-run@grocerease-5abbb.iam.gserviceaccount.com`. The GitHub deployer
needs metadata-only permission to describe the latest versions (for example,
`roles/secretmanager.viewer`); it does not need access to their payloads.
Cloud Run validates the runtime's secret access again when it creates the API
revision and updates the job.

### Private bucket and identities

Grant the API runtime identity object create/read/delete access to the dedicated
print bucket. It also needs `iam.serviceAccounts.signBlob` on itself so it can
create short-lived V4 URLs; `roles/iam.serviceAccountTokenCreator` on that one
service account supplies that permission. The deployer needs permission to
describe the bucket and read both IAM policies. CI requires direct
`roles/storage.objectAdmin` on the bucket and a direct self-grant of
`roles/iam.serviceAccountTokenCreator`; this deliberately rejects an implicit
or ambiguous bootstrap before checkout is enabled.

Create the scheduler identity once:

```bash
PROJECT_ID=grocerease-5abbb
REGION=us-central1
RUNTIME_SA="fridgie-api-run@${PROJECT_ID}.iam.gserviceaccount.com"
SCHEDULER_SA="fridgie-print-scheduler@${PROJECT_ID}.iam.gserviceaccount.com"
PRINT_JOB=fridgie-print-reconciliation
PRINT_SCHEDULER=fridgie-print-reconciliation

gcloud iam service-accounts create fridgie-print-scheduler \
  --project="$PROJECT_ID" \
  --display-name="Fridgie print reconciliation scheduler"
```

Do not remove `roles/cloudscheduler.serviceAgent` from Google's Cloud Scheduler
service agent. The human/bootstrap identity also needs permission to act as
`$SCHEDULER_SA` while creating the OAuth target.

### Bootstrap the job and scheduler

CI intentionally requires the job to exist before the commerce gate can be
enabled. That makes job-level Scheduler IAM an explicit reviewed bootstrap
step. Use the image already serving the API to create a harmless placeholder;
the first gated CI run replaces its application-level configuration before the
print-enabled API candidate receives traffic.

```bash
CURRENT_IMAGE=$(gcloud run services describe fridgie-api \
  --project="$PROJECT_ID" --region="$REGION" \
  --format='value(spec.template.spec.containers[0].image)')

gcloud run jobs create "$PRINT_JOB" \
  --project="$PROJECT_ID" --region="$REGION" \
  --image="$CURRENT_IMAGE" --command=bun --args=--version \
  --service-account="$RUNTIME_SA" \
  --tasks=1 --parallelism=1 --max-retries=0 --task-timeout=10m \
  --cpu=1 --memory=1Gi

gcloud run jobs add-iam-policy-binding "$PRINT_JOB" \
  --project="$PROJECT_ID" --region="$REGION" \
  --member="serviceAccount:${SCHEDULER_SA}" \
  --role=roles/run.invoker

gcloud scheduler jobs create http "$PRINT_SCHEDULER" \
  --project="$PROJECT_ID" --location="$REGION" \
  --schedule='*/15 * * * *' --time-zone=Etc/UTC \
  --uri="https://run.googleapis.com/v2/projects/${PROJECT_ID}/locations/${REGION}/jobs/${PRINT_JOB}:run" \
  --http-method=POST \
  --oauth-service-account-email="$SCHEDULER_SA" \
  --oauth-token-scope=https://www.googleapis.com/auth/cloud-platform \
  --max-retry-attempts=0
```

The zero Scheduler retries and zero Cloud Run task retries are intentional.
The next regular tick safely resumes durable work, while automatic platform
retries can overlap an ambiguous provider request. Before enabling commerce,
manually execute the placeholder once and confirm the Scheduler delivery is
authenticated. After the first gated deploy, execute the real job once and
confirm its JSON result and zero exit status.

### Required GitHub repository variables

Set every value in this table before setting the opt-in gate. CI rejects empty,
malformed, or incoherent combinations.

| Variable | Staff sandbox value / rule |
| --- | --- |
| `LULU_ENV` | `sandbox` |
| `LULU_SOFTCOVER_POD_PACKAGE_ID` | Authenticated, proven softcover SKU |
| `LULU_HARDCOVER_POD_PACKAGE_ID` | Authenticated, proven casewrap SKU; casewrap remains preflight-gated |
| `LULU_COST_SHIPPING_FIELD` | Authenticated probe result: `shipping_option` or `shipping_level` |
| `LULU_PRODUCTION_DELAY_MINUTES` | `1440` |
| `PRINT_STORAGE_BUCKET` | Dedicated private bucket name, without `gs://` |
| `PRINT_ORDER_ARTIFACT_RETENTION_DAYS` | Privacy-policy retention, currently `120` |
| `PRINT_SUPPORT_EMAIL` | Monitored support address |
| `PRINT_MARKUP_BPS` | Reviewed integer basis points, `0` through `100000` |
| `PRINT_QUOTE_CURRENCY` | Three uppercase letters, currently `CAD` |
| `STRIPE_TAX_ENABLED` | `true` after registrations and product settings are complete |
| `STRIPE_PRINTED_BOOK_TAX_CODE` | Reviewed Stripe code, default `txcd_35010000` |
| `STRIPE_SHIPPING_TAX_CODE` | Reviewed Stripe code, default `txcd_92010001` |
| `PRINT_ALLOW_UNAVAILABLE_TAX` | Normally `false`; `true` only after the legal review described above |
| `PRINT_PRODUCTION_ENABLED` | `false` for sandbox and while live checkout is intentionally disabled |
| `PRINT_LULU_VALIDATION_ACKNOWLEDGED` | `false` until the Lulu production blocker is resolved |
| `PRINT_ALLOW_SANDBOX_IN_PRODUCTION` | `true` for the staff sandbox; `false` with `LULU_ENV=production` |
| `PRINT_COMMERCE_ENABLED` | Set to `true` last |

The workflow always forces `PRINT_REPRINT_EXECUTION_ENABLED=false` in the API
and scheduled worker. Approved reprints remain an operator-only execution.
`PRINT_AMBIGUOUS_RETRY_MINUTES` is fixed at 15 in deployment even though local
development can override it.

For live mode, install matching live secret versions, set
`LULU_ENV=production`, set `PRINT_ALLOW_SANDBOX_IN_PRODUCTION=false`, and keep
`PRINT_PRODUCTION_ENABLED=false` through the configuration deploy. Only after
the production checklist is complete should an operator set both
`PRINT_LULU_VALIDATION_ACKNOWLEDGED=true` and
`PRINT_PRODUCTION_ENABLED=true`. Setting the production flag back to `false`
is the emergency checkout kill switch while reconciliation remains available
for existing orders.

Do not turn `PRINT_COMMERCE_ENABLED` off as a kill switch after deployment. The
disabled path intentionally refuses to erase attached print configuration. To
fully decommission, first drain/reconcile existing orders, pause Scheduler,
remove the API bindings in a reviewed manual change, and only then set the gate
to `false`.

The EAS/native build has a separate configuration boundary. Set
`EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY` and the wallet variables in the EAS
environment before creating a staff or production build; API Secret Manager
bindings do not populate Expo build-time variables.

The print worker is updated before API promotion. If that succeeds but a later
promotion or Discover update fails, API traffic rollback does not roll the
Cloud Run Job revision back; inspect the job image/config after an ambiguous
workflow failure before re-running it. CI never executes the reconciliation
job during deployment.

## 6. Live launch checklist

1. Complete every sandbox probe above with saved request/response evidence.
2. Confirm exact hardcover casewrap template geometry for every supported page
   band. Until then, hardcover preview carries a blocking preflight error.
3. Confirm Lulu normalization, saved payment/autopay, production delay, and a
   cancellation/recovery procedure with Lulu.
4. Verify Stripe manual capture, 3DS, Apple Pay, Google Pay, refund, webhook
   replay, and tax transaction/reversal behavior on physical devices.
5. Verify bucket IAM, V4 URL signing, lifecycle, scheduled reconciliation, and
   operational access to immutable order artifacts.
6. Replace sandbox/test keys with matching production/live secrets.
7. Set `LULU_ENV=production`, then and only then set both production gates true.
8. Place and inspect one explicit staff-approved production proof order before
   opening checkout broadly. Never automate this proof order.
